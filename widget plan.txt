RSS Feed Widget – Technical Options and Code Maintenance

Current setup (context)





Page: rss_feed/data/stock_matches.html – loads records from Excel via the server (search, upload stock list, filter, PDF analysis). The file is generated by rss_feed/rss_feed.py (large inline HTML/CSS/JS string) and served by rss_feed/rss_feed_server.py at /, /page, /stock_matches.html.



Backend: Python HTTP server; APIs: /all, /search, /search_with_file, /process_pdfs, /process_documents, etc. Data lives in data/rss_feed.xlsx.

To get a window that floats over other apps/browsers/desktop and is movable and resizable, the content must run inside a desktop window (not a normal browser tab). Below are the main technical options and how they affect code maintenance.



Technical options for the widget

Option A: Electron





Idea: Small desktop app with a frameless, always-on-top window that loads the same URL (e.g. http://127.0.0.1:5005) or the same HTML file. Move/resize via a title bar + resize handles; Electron main process sets window position/size.



Floating: Yes (always-on-top, over all other windows).



Move: Title bar with -webkit-app-region: drag or JS + IPC to BrowserWindow.setPosition.



Resize: Draggable edges/corners in the page; JS calls IPC to BrowserWindow.setBounds / setSize.



Backend: Existing Python server runs separately, or Electron can start it (e.g. child_process.spawn).



Pros: Same HTML/JS/CSS as the full page; mature ecosystem; full control over window behavior.



Cons: Heavier (Chromium); extra Node/Electron setup and packaging.

Option B: Tauri





Idea: Same as Electron but with a Rust core and system WebView. One small window, frameless, always-on-top, load same URL or local HTML.



Floating / Move / Resize: Tauri window APIs (e.g. set_position, set_size, set_always_on_top); drag/resize implemented in the frontend and exposed to Rust via Tauri commands if needed.



Backend: Python server runs separately (widget just opens the URL).



Pros: Lighter binary; same frontend code; good window control.



Cons: Rust toolchain; separate Tauri project to maintain.

Option C: Python + pywebview





Idea: Python script creates a frameless window with pywebview and loads http://127.0.0.1:5005 (server must be running). Always-on-top and move/resize are platform-dependent (may need a custom window implementation or a second layer).



Floating: Possible on some platforms with window.on_top = True (or equivalent); less uniform than Electron/Tauri.



Move/Resize: Often implemented in HTML/JS (drag bar, resize handles); moving/resizing the actual window may require platform-specific code or a thin native wrapper.



Pros: Stays in Python; reuses existing server; minimal new stack.



Cons: Less predictable “over everything” behavior; may need native code for full parity with Option A/B.

Option D: Python + Qt (PyQt6 / PySide6) + QWebEngineView





Idea: Qt window with QWebEngineView loading the same URL. Window is frameless, always-on-top; custom title bar for drag; resize by handling mouse on window edges or via resize handles.



Floating / Move / Resize: Full control in Python (e.g. setWindowFlags, move, resize, mouse events).



Backend: Same Python server; widget is a separate Python script that opens a Qt window.



Pros: Full control; same frontend; single language (Python) for the launcher.



Cons: Qt + WebEngine dependency (large); licensing (PySide6 is LGPL).

Option E: Browser popup / secondary window





Idea: window.open(..., 'width=400,height=600') and let the user move/resize the browser window.



Floating: No – the window stays within the browser and does not overlay other applications or the desktop.



Conclusion: Does not meet “floating over other apps/browsers/desktop”; only useful as a small companion window inside the browser.



Recommendation (short)





For reliable “over everything” + move + resize and same HTML/JS as the current page: Electron (A) or Tauri (B) are the most straightforward. Choose Electron if you prefer Node/JS tooling; Tauri if you want a smaller binary and are okay with Rust.



If you want to stay in Python only: Qt + QWebEngineView (D) gives the most control; pywebview (C) is simpler but may need extra work for true overlay and smooth move/resize on all platforms.



Code maintenance: same vs different code for page vs widget

Option 1: Single codebase, two “modes” (recommended)





One HTML/JS/CSS codebase (or one generated output).



Full page: Opened in a normal browser (or full-size Electron/Tauri window) at the same URL.



Widget: Same URL (or same HTML) opened in a small, frameless, always-on-top window. No duplicate UI logic.



Differentiation: Either by query param (e.g. ?mode=widget) or by detecting the host (e.g. in Electron, window.electronAPI exists). Based on that:





Apply widget-only CSS (e.g. compact layout, optional title bar for drag).



Optionally hide or simplify some sections (e.g. theme toggle in a compact header).



Add widget-only JS: drag region, resize handles, “minimize”/“pin” if you add them later.



Generation: Keep generating a single stock_matches.html from rss_feed.py; add a small block of widget-specific CSS/JS that runs only when mode=widget or in the widget host. No second HTML file.

Pros: One place to change behavior and fix bugs; widget and page stay in sync.
Cons: Conditional logic and a bit of widget-specific code inside the shared file.

Option 2: Two separate frontends





Full page: Current (or refactored) stock_matches.html as now.



Widget: A separate HTML (e.g. stock_matches_widget.html) or a separate app (e.g. widget/ in Electron) that duplicates or imports the table, search, and API logic.



Sharing: Either copy-paste (drift risk) or extract shared JS/CSS (e.g. app.js, styles.css) and have both the page and the widget load them. Backend APIs stay the same.

Pros: Widget can diverge freely (different layout, features).
Cons: Two UIs to maintain; easy to fix one and forget the other unless you have shared modules and tests.

Option 3: Single codebase with a shared “core” and two shells





Refactor so that the current inline HTML in rss_feed.py is split into:





Core: Shared JS (API calls, table rendering, search, upload) and shared CSS (variables, table, modal). Either one core.js / core.css file or a small bundle.



Shells: (1) Full-page shell: stock_matches.html – full layout, theme toggle, all sections. (2) Widget shell: minimal HTML that loads the same core + widget-specific wrapper (drag, resize, compact layout).



Generation: rss_feed.py could emit both HTML files from templates, or emit one and the widget shell is a static file that loads the same API and core JS. Server serves both.

Pros: Clear separation; widget and page share all business logic; future changes to “load records from Excel” or search apply once.
Cons: Refactor effort up front; need a simple way to load the core (e.g. script tags from the same server).



Suggested direction (for the next step)





Choose a host technology (Electron, Tauri, or Python+Qt) based on your preference: Node vs Rust vs Python-only.



Adopt single codebase, two modes (Option 1) so the widget is the same page in a different window type; add ?mode=widget (or host detection) and a small amount of widget-only CSS/JS for drag and resize. This keeps maintenance low and avoids duplicating the table/search/API logic.



Later, if the widget or page diverges a lot, you can refactor toward Option 3 (core + two shells) so both the full page and the widget are thin shells around the same core.

Once you pick the technology (A–D) and the maintenance approach (1–3), the next step is to define the functional flow and specifications of the widget (what stays, what is simplified, what is new), and then implement the floating, movable, and resizable behavior accordingly.
